Craft Docs

Craft

craft is Craft’s terminal coding agent: a TUI (or --print headless) harness written from scratch in Rust on top of the animist provider/agent/history stack, with the argosy knowledge crate linked in-process.

It is designed to spend as few tokens as possible without giving up speed or ergonomics. Most coding agents burn context reactively — wait until the window is full, then summarize everything in one expensive pass. Craft keeps context lean continuously, so the model spends tokens on your work instead of on stale reads and verbose tool output:

  • Tool output is pre-compressed before it ever enters history — code, logs, diffs, JSON arrays, and search results each get a tailored compressor.
  • Stale and superseded file reads are replaced with compact markers before each turn.
  • Deterministic (no-LLM) compaction kicks in at 60% of the context window; an LLM summarization pass only runs at 80% if the cheap stage wasn’t enough.
  • Compressed originals stay retrievable — durably, from the history entry itself — in any later turn or after a session reload.
  • Subagents run in their own context windows, so delegation never pollutes the main session.

What’s in the box

  • A native terminal UI (superlighttui): fast startup, 30 themes, command palette, fuzzy search, plan mode, subagent chat windows.
  • Subagents and parallel dispatch: the task tool with model tiers and optional worktree isolation; batch fans children out concurrently.
  • MCP servers over stdio and HTTP.
  • Skills and recipes: reusable workflows as markdown skills, parameterized YAML/JSON blueprints.
  • An ACP server (craft acp) for editor/IDE integration.
  • Permissions and snapshots: tree-sitter bash parsing, allow/deny/ask rules, /undo, and an OS sandbox.
  • Argosy knowledge: semantic search and ask, review sessions with P0–P3 findings, and post-turn memory extraction — in-process, local embeddings.

This repository is mid-migration. The active agent lives in agent/ (crate craft, binary craft); the root CraftCode app is being reworked and is not documented here yet. These docs cover the CLI harness only.

Honesty note

A large share of the codebase was written by an AI, guided by humans. Being upfront about how software is made matters.

Quick Start

Install

Install from the repository (installs the binary as craft):

cargo install --locked --git https://github.com/craft-build/craft.git craft

Or build from a checkout:

git clone https://github.com/craft-build/craft.git
cd craft
cargo build -p craft --release
# binary at target/release/craft

The self-updater is built in: craft update applies a digest-pinned update and craft rollback undoes one.

API keys

craft never stores secrets in its config — api_key_env names an environment variable that holds the key:

export ANTHROPIC_API_KEY=sk-ant-…
# or OPENAI_API_KEY=…, SYNTHETIC_API_KEY=…, ZHIPU_API_KEY=…

On first run, craft auto-detects providers from credential environment variables when the config declares none, so the fastest path to a working agent is: export one key, run craft.

Run

From your project directory:

craft

Type a prompt, press Enter, and the agent starts working. A startup prompt also works without the TUI:

craft "find the flaky retry test and fix it" --print

Useful first commands inside the TUI:

  • /model — pick a model (configured models merge with live listings and the models.dev catalog).
  • /sessions — list and resume sessions.
  • /usage and /stats — token spend and session stats.
  • Ctrl-H — keybindings; Ctrl-P — command palette.

Configuration

Configuration lives in BML format at ~/.config/craft.bml (or split across ~/.config/craft/*.bml). A minimal provider setup:

provider "anthropic" {
  kind = "anthropic"
  api_key_env = "ANTHROPIC_API_KEY"
}

Local models work too — a keyless loopback endpoint needs no key at all:

provider "local" {
  kind = "openai-compatible"
  base_url = "http://localhost:8080/v1"
}

See Configuration for the full file layout and Providers for every provider kind. A fully commented example ships in the repository as agent/agent.example.bml.

Configuration

Configuration lives in BML format (barkml):

  • ~/.config/craft.bml — the main file, or
  • ~/.config/craft/*.bml — split files that merge together.

A legacy ~/.craft/ location is still searched. A missing file is an empty configuration; malformed files, unknown fields, invalid URLs, and invalid limits are errors. Loading never writes files or contacts a provider.

On first run, providers are auto-detected from credential environment variables when the config declares none.

A fully commented example ships as agent/agent.example.bml — it is the canonical reference for every key below.

Providers

Providers are configured by alias in the BML config; each [providers.<alias>] chooses a kind. Multiple aliases may use the same kind with different credentials, URLs, and model catalogs.

api_key_env names an environment variable, not the key itself — keep secrets in your shell or secret manager. With overrides, api_key_env defaults to the provider’s usual key variable (OPENAI_API_KEY, ANTHROPIC_API_KEY, …).

Supported kinds: anthropic, openai, openai-compatible, synthetic, zai-coding-plan, ollama, llama-cpp, omlx, amazon-bedrock.

anthropic

provider "anthropic" {
  kind = "anthropic"
  api_key_env = "ANTHROPIC_API_KEY"
}

Accepts base_url for Anthropic-compatible services — supply the complete base URL including any path prefix.

openai

Speaks the Responses API by default; protocol = "chat_completions" selects Chat Completions. Both accept base_url, plus organization and project.

provider "openai" {
  kind = "openai"
  api_key_env = "OPENAI_API_KEY"
}

openai-compatible

Any OpenAI-dialect endpoint, over Chat Completions:

provider "deepseek" {
  kind = "openai-compatible"
  base_url = "https://api.deepseek.com/v1"
  api_key_env = "DEEPSEEK_API_KEY"
}

A keyless local endpoint (loopback or private host, no key configured) automatically rides animist’s keyless llama.cpp client — local llama.cpp, vLLM, and LM Studio servers work with no dummy key. Non-local hosts require a key.

This is also the migration path for every dropped vendor kind (below).

AWS_PROFILE, SSO, assume-role, credential_process, web identity, container/IMDS roles) and takes its region from AWS_REGION/AWS_DEFAULT_REGION, the active profile, or region on the provider. Model catalogs

[providers.<alias>.models."<exact-model-id>"] declares or partially overrides a model:

model "my-coding-model" {
  context_length = 32768
}

Overridable metadata: name, description, context_length, max_output_tokens, supports_thinking, requires_thinking, protocol, reasoning_options (e.g. [{ type = "effort", values = ["low", "high"] }]). Local backends can declare thinking_fields with JSON-shaped BML fragments keyed by off, adaptive, or effort level; those fragments are deep-merged into the request.

Discovery merges configured models with live provider listings and the models.dev catalog (disk-cached 24 h), sorted by ID; discover_models = false disables listing. Discovery errors propagate rather than silently yielding an empty catalog. Token limits are catalog metadata — they feed compaction thresholds and usage display, not request parameters. Set [agent].max_tokens for an output cap.

Unknown models fall back to provider/family dialects; discovery is advisory, not a reason to reject an otherwise usable model ID. craft models lists what a config resolves to.

Dropped kinds

The predecessor’s vendor-specific kinds are dropped (unsupported since the animist cutover): azure, chatgpt, cohere, copilot, deepseek, doubleword, gemini, groq, huggingface, hyperbolic, llamafile, minimax, mira, mistral, moonshot, openrouter, perplexity, together, venice, voyageai, xai, xiaomimo, zai. A config naming one fails with an actionable error; the OAuth/device flows (chatgpt, copilot) are gone with their kinds.

Migration for any OpenAI-dialect vendor is to point openai-compatible at its base URL:

# before: kind = "deepseek"
provider "deepseek" {
  kind = "openai-compatible"
  base_url = "https://api.deepseek.com/v1"
  api_key_env = "DEEPSEEK_API_KEY"
}

Context Management

Craft keeps context lean continuously instead of summarizing reactively when the window fills. Four mechanisms work together: pre-compression, the read lifecycle, staged compaction, and an overflow ladder. All of them are reversible — originals are never deleted.

Tool-output compression

Between runs, an alteration pass classifies every oversized tool result by content type — code, log, diff, JSON array, search result, plain text — and rewrites it into a compact marker as a history revision. Log and code compression use an aho-corasick keyword classifier (error, warning, security, definition, import, …) so the lines that matter survive.

The verbatim originals stay in the entry sources, and the retrieve tool restores them by content hash:

[137 lines compressed from 892. Retrieve original: hash=a91f33c2]

Nothing lives in a side store: a marker survives session reloads, and retrieval works in any later turn. Within a run, the request layer recomputes only the run’s own suffix (everything older arrives pre-altered).

Tuning lives in the [compression] block — rates, line caps, per-file match caps, and protect_recent_tool_outputs (the last N tool outputs stay verbatim). See Configuration.

Read lifecycle

File reads are tracked fresh → stale → superseded. As the conversation moves on:

  • stale reads get durable marker revisions, so old snapshots stop occupying context;
  • superseded reads (the file was edited since) collapse the same way;
  • retrieve still serves the original bytes from the entry source.

Two-stage compaction

[[compaction]] entries configure staged compaction, each with a kind and a context fill ratio. Between runs the driver estimates history size and runs every armed stage whose threshold is crossed, lowest ratio first:

compaction "vcc" {
  context = "0.6"
}
compaction "llm" {
  context = "0.8"
}
  • vcc — deterministic, no-LLM compaction: the head of the history is replaced by a structured summary entry (tagged craft.compaction); the recent tail is kept verbatim; repeated runs merge with the previous summary.
  • llm — one-shot summarization call replacing the head with a handoff summary (deterministic fallback if the call fails).

Omitting the blocks defaults to vcc at 0.6 then llm at 0.8.

Effectiveness gating skips a stage whose last run saved under 10% of estimated context until another stage compacts effectively, so compaction never cycles. Sessions without a known context_length never compact. Compacted-away entries are deactivated, never deleted — their originals stay in entry sources for retrieve.

compaction_buffer (absolute tokens ≥ 1000, or a quoted percent like "20%") reserves headroom so compaction fires before the window fills.

Overflow recovery

When a request still overflows after compaction, an escalating ladder collapses tool results progressively — 10%, 20%, 50%, 100% — before failing the turn. A failed run keeps whatever compaction it did; originals are never lost.

Dedup cache

Identical read-only tool invocations return cached output; entries are invalidated structurally when files change. The dedup Respond runs in the guardrail layer.

Compaction on demand

/compact in the TUI runs the compaction stages immediately. Compaction summaries render as cards in the transcript (see Sessions).

The Harness

One long-lived harness::Conversation per session drives an animist Agent over an animist History; surfaces never run a loop of their own. This page describes what runs under the TUI, --print, and ACP alike.

Runtime setup contract

Every execution surface obtains the shared pieces of a session from agent/src/runtime.rs, so equivalent sessions receive equivalent run policies:

  • runtime::workspace_env(cwd, mcp) — instruction discovery, the workspace (MCP handle installed), and the permission engine. Every surface constructs the PermissionManager and consults it: the TUI prompt overlay, the ACP session/request_permission, and the headless permission gate.
  • model_selection::resolve_or_default — a model choice plus its catalog window; output ceilings ride the model handle, where request shaping reads them. Lookup only: --model ids the catalog does not list stay usable.

The layer chain

Craft policy lives in an ordered AgentLayer chain (head → tail):

  1. PolicyLayer — permission rules → auto-review → the approval responder → the plan-mode gate.
  2. GuardrailLayer — doom-loop detection (grace/hard-stop), per-tool guardrails, dedup Respond.
  3. RequestLayer — the per-request view: in-run read-lifecycle and compression rewrites, Chat-Completions image relocation, the output-token clamp, sampling options, fallback-model selection.
  4. RecoveryLayer — recover: linear backoff, API-key rotation, model fallback chain, reauth wait, overflow compaction.
  5. ContinuationLayer — MaxTokens continuation and stalled-turn nudges as step_end appends.
  6. SnapshotLayer — /undo pre-captures at the tail, so only calls that really run are captured.
  7. PersistLayer — flushes the history change feed to the session log.

The driver

A thin driver (harness::driver::run_turn) does what no hook can: builds the input, runs and awaits the agent, adds terminal markers, runs the between-run alteration/compaction passes, and re-runs for the advisor and ContextWindowExceeded.

Model switching happens between runs by rebuilding the agent on the same history handle; fallback models inside a run go through the request layer.

Subagents

The task tool spawns child agents as their own Conversation with:

  • a fresh history — delegation never pollutes the main session;
  • a restricted tool registry;
  • their own layer instances built from the parent’s shared services;
  • model tiers (weak / medium / strong, capped at the parent’s tier);
  • cancel tokens, optional worktree isolation, and optional JSON-schema-validated output.

batch fans children out concurrently under the parent’s claims and budgets.

In the TUI, each subagent gets its own chat window (Ctrl-N / Ctrl-P; /tasks view). See Tools for the tool surface and TUI for the windows.

Advisor

An optional post-turn reviewer (agent.advisor, off by default) reads each reply and emits at most one note. auto_act (off / nit / concern / blocker) sets the minimum severity that triggers an automatic follow-up turn instead of stopping, bounded by max_act_turns.

Tools

All tools use strict typed JSON arguments and produce literal text for the model.

Filesystem

  • read — numbered lines, offset/limit paging, continuation notices.
  • grep — regex or literal, ignore-aware, bounded scan budget.
  • edit / inplace_edit / multiedit / fuzzy_replace / apply_patch — replace-based editing with fuzzy matching; edit_lines-style line edits and multi-edit batches ride these.
  • write, delete, move_file — the canonical mutations (move_file is the sanctioned move; see permissions).
  • glob, list — discovery.

Editing stages beside the destination and atomically replaces it, preserving permissions and bytes outside the replacement.

Execution

  • bash — with bash_status, bash_watch, bash_kill for background tasks; sandbox profiles; tree-sitter command parsing for permission scoping. Default timeouts come from the [bash] config (Configuration).
  • batch — parallel dispatch of independent tool calls under the parent’s budgets.
  • code — Python orchestration: one script drives the same tools with real awaits (codemode). Off by default; enabled per session with --codemode//codemode or the [codemode] config.
  • worktree — linked worktree creation for isolated mutations.

Interaction and support

  • question — structured user prompts during a run.
  • todo_write — plan-mode todo cards.
  • view_image — images as vision input.
  • webfetch — SSRF-guarded URL fetching (private/loopback IP and redirect checks). Timeout and retry defaults come from the [webfetch] config (Configuration).
  • websearch — web search.
  • sessions — session listing.
  • skill / list_skills — skill discovery and loading.
  • review, task, retrieve, list_tools — see Review, The Harness, and Context Management.

Argosy knowledge

Linked in-process (no subprocess, no MCP transport): semantic search and ask, document/memory/rule reads and writes, and the review session toolset. See Argosy.

MCP tools

MCP servers register as server__tool portable tools. See MCP.

Paths and limits

Paths are workspace-relative or absolute beneath the canonical workspace root; .., .git, and symlink components are refused.

Text tools support UTF-8 files up to 8 MiB, including CRLF. Reads and searches bound excerpts to 64 KiB (individual lines to 2048 bytes) and report incomplete results rather than implying exhaustiveness.

Workspace checks are guardrails for a trusted local project, not an OS security sandbox; the host supplies approval hooks and sandbox policy before exposing the agent to untrusted workspaces.

Sandbox

The bash tool runs under an OS command sandbox configured by the [sandbox] section:

sandbox {
  enabled = true
  mode = "workspace_write"   # workspace_write (default) | read_only | danger_full_access | off
  network = true             # false blocks sandboxed network access
}

Backends

  • macOS — the stock sandbox-exec.
  • Linux — argv is wrapped with bubblewrap (bwrap, prerequisite).

Enforcement is fail-closed

On supported platforms, if the backend binary is missing while confinement is requested, the command errors before it starts — install it or set sandbox.mode = "off". On platforms without a sandbox implementation, commands run unsandboxed with a visible one-time note.

Escape hatches

  • --yolo disables the sandbox entirely (predecessor parity).
  • CRAFT_SANDBOX=off is the documented env escape hatch with highest precedence (debug/CI).

Plan mode and read-only workers

Plan-mode turns and read-only workers (the reviewer subagent, research subagents) run bash read-only; the allocated plan file stays writable via an exact-path grant.

See Permissions & Snapshots for the approval rules that sit on top, and Configuration for where the block lives.

Permissions & Snapshots

Rules

Permission rules are BML blocks — allow / deny / ask — scoped to bash or MCP, with wildcards. They live in a permissions.bml next to the config or in a project’s .craft/ directory.

Bash commands are parsed with tree-sitter, so compound commands request each sub-command’s approval separately: git diff && rm -rf / asks for git * and rm * approval separately. Subshells, command substitution, and pipes are handled the same way — most agents only see the first command.

Every surface enforces

The TUI prompt overlay, the ACP session/request_permission, and the headless gate all consult the same PermissionManager built by runtime::workspace_env.

Headless runs (--print, term run, recipe run) enforce the same rules with no interactive approver: unresolved asks fail closed with guidance naming the opt-outs, and denied calls never execute. The gate covers batch children and subagent dispatch.

Opt-outs

  • --yolo / --dangerously-skip-permissions — bypass everything, disables the sandbox.
  • -A / --auto-review — an LLM (or decision-endpoint) reviewer answers permission prompts, fail-closed below a confidence threshold.

They are mutually exclusive and rejected at Cli::validate.

Tool policy flags

  • --allowed-tools pre-approves tools (scope-universal allow rules — every tool stays advertised; it does not restrict the tool set).
  • --disallowed-tools denies tools at the permission gate (calls fail with a permission-denied message; batch children and subagents are covered).

Both accept PascalCase or snake_case native names (Read, bash) and MCP forms (server__tool, mcp__server__tool, mcp__server for a whole server). Unknown names error with the valid-tool list; a tool named by both flags is a hard error. The rules live for the process only — they never persist into sessions or permissions.bml.

--permission-mode maps to the same posture: default, plan (plan mode; conflicts with an explicit --mode build), or bypassPermissions (matches --yolo).

Snapshots and /undo

Files are snapshotted before mutations — first-wins, ≤ 5 MiB, text only — and /undo walks them back.

Undo restores file contents only; deactivated history entries survive in session sources but are not restored.

Auto-review mode

With -A, every permission prompt is answered by an LLM reviewer that sees the command and its context. Low confidence fails closed, so a confused reviewer can never silently approve a dangerous call. /auto-review toggles it from the TUI.

Auto-review can also be the default posture — no flag needed. In the global config (~/.config/craft.bml or a split ~/.config/craft/*.bml, e.g. a permissions.bml there), set it inside the permissions block:

permissions {
  auto_review = true
}

A project’s .craft/permissions.bml sets the same key at the top level — auto_review = true beside its tool blocks — and its value wins over the global one. Every surface starts with the reviewer on: the TUI installs it at startup, and headless runs (--print, term run, recipe run) install it whenever the flag or the config enables it. -A implies the same posture; --yolo still bypasses prompting entirely, and the two stay mutually exclusive. There is no off flag — /auto-review toggles the current session. ACP sessions never install a reviewer locally, so an enabled auto-review still falls through to the client’s permission prompt.

Argosy

The argosy knowledge crate is linked in-process — no subprocess, no MCP transport. Its tools register as first-class native tools with the same typed-JSON interface as the builtins.

Argosy keeps its own state keyed by project root: writes from craft are visible to the standalone argosy mcp server, and vice versa. Embeddings run locally (ONNX, via the argosy crate) — nothing leaves your machine for indexing.

Search and ask

  • search — hybrid semantic search over the project’s knowledge (documents, memory, skills, rules): exact-term BM25 and vector similarity fused by reciprocal rank fusion. Exact identifiers and rule IDs rank alongside paraphrases.
  • ask — retrieval augmented by an optional Jev-compatible decision endpoint: hybrid-retrieves candidates, then asks the endpoint which (if any) answers the question, returning the selection with a calibrated confidence.

Retrieval is passage-level: hits carry the matched passage, a heading breadcrumb, and line numbers, so the agent often answers without a further read.

Documents, memory, rules

Reads and writes for every concept kind: documents (curated project knowledge), memory (session learnings), and styleguide rules (conventions the project wants enforced). Writes reconcile the index immediately.

Skills

Project-stored skills join the skill tool’s discovery with shadowing precedence (see Skills & Recipes).

Review toolset

Grounded like argosy mcp: start_review, review_diff, report_finding, review_findings. start_review runs the deterministic styleguide pattern pre-pass over the diff’s added lines; report_finding validates rule URIs. See Review.

Memory extraction

Post-turn memory extraction (on by default; agent.memory_extraction) writes durable facts from a turn into the project’s local argosy, so future sessions find them via search. /memory opens the workflow in the TUI.

Review

Craft ships a reviewer workflow on top of the argosy review toolset.

The reviewer subagent

/review — or the review tool — snapshots the working-tree diff (or the current state of named paths, with paths for a whole-area review of unchanged code) and returns prioritized P0–P3 findings with a verdict.

The reviewer is read-only: it records findings through report_finding, never edits files.

The session flow

  1. start_review snapshots the git diff — local tracked changes against a base (HEAD by default), exactly one commit, or the current state of named paths (base "empty" materializes every tracked line as added).
  2. A deterministic pattern pre-pass runs immediately over the added lines when the project’s argosy holds styleguide rules with a pattern — those findings land first, confidence 1.0.
  3. The reviewer agent reads the diff, checks the rules, and reports verified defects with report_finding: priority, confidence, affected lines, rule URIs, and a machine-applicable fix when one exists.
  4. review_findings lists the set (filterable by priority and path) and can export SARIF for GitHub code scanning or reviewdog JSONL for one-click PR comments.

Findings are validated against the snapshot — the path must be a changed file and the line range must fall inside the changed hunks.

Related commands

  • /scan — the same machinery aimed at the current state of the codebase.
  • /dream — speculative/exploratory review mode.
  • /memory — memory workflow over the argosy.

Findings from review sessions are grounded: rule URIs must resolve to styleguide-rule concepts in the project’s argosy (see Argosy).

Skills & Recipes

Skills

Skills are reusable workflows: markdown with instructions and frontmatter, discovered from two sources:

  • bundled — shipped with the binary (e.g. debugging, run, verify, stuck, agents-md-init);
  • filesystem — project-stored skills (.craft/skills/) join discovery via argosy.

Discovery is surfaced through list_skills (origin, kind, shadowing status, trust tier); loading goes through the builtin skill tool. Local skills shadow bundled ones by name.

Skill bodies are trusted instructions only when their provenance is: imported argosy skills arrive wrapped as untrusted content, capped at the user’s configured trust.

Recipes

Recipes are parameterized YAML/JSON blueprints rendered with minijinja and run via the CLI:

craft recipe list
craft recipe run <name> [params…]

Recipe runs are headless surfaces: they enforce the same permission gate as --print, with the same opt-outs.

Custom slash commands

Custom namespaced slash commands are discovered from project config; --no-commands skips discovery in the TUI. /recipe picks a recipe interactively.

TUI

The terminal UI is built on superlighttui: native, no JavaScript runtime, fast startup and a high frame rate even on small laptop screens. craft starts it by default.

Daily driving

  • Prompt — type and press Enter. A positional PROMPT argument submits as the first message; piped stdin (echo "do x" | craft) is read the same way.
  • Plan mode — Tab toggles build/plan. The plan form and todo cards keep the plan first-class; plan-mode turns run read-only (see Sandbox). The mode persists in the session and is restored on resume.
  • ! and !! — run a bash command with or without the agent seeing the output.
  • Editor integration — Ctrl-O / Alt+O opens the input (or a file) in $EDITOR.

Themes

Thinking

/thinking opens the selector; /thinking low, /thinking adaptive, /thinking off, or /thinking 4096 apply directly. Alt+E cycles. The preference is persisted with the session, restored on resume, and inherited by subagents. Details in CLI → Thinking controls.

Sessions

Sessions are crash-safe append-only JSONL files with an index, archive, and usage ledger (craft stats, /stats).

Format

Messages persist as animist entry records (log format 4): entry, insert, revise, deactivate, replace, mapping one to one onto the history change feed — plus sub_entry subagent histories and the trailing meta record.

One loader reads every older shape (pre-animist message records, .json files) and folds their raw tool_outputs copies into entry sources; saving rewrites the current shape. A corrupt or truncated trailing record is skipped with a warning; a record whose index is out of range for the replayed list fails the load with an actionable error.

One-way upgrade: older craft builds cannot read the new saves — upgrade before rolling back.

Resume

/sessions (TUI), -c / --continue (latest), -s/--session <id> (specific), and ACP session/load all replay the same shared transcript builder:

  • inactive (compacted-away) entries are hidden;
  • compaction summaries render as cards;
  • markers render by tag — altered tool results show their altered text with the verbatim original one click away (see Context Management).

--fork-session copies a --session/--continue source under a new id without touching the source. --session-id sets the persistence id for a new session; it never resumes.

Mode persistence

The TUI persists its mode (build/plan) in the session file on every user-initiated change (Tab toggle, implementing a plan). A resumed session restores its stored mode — the stored mode wins over --mode/--permission-mode plan, which seed fresh sessions and legacy sessions with no stored mode. The stored model is restored too (unless -m overrides it).

Print-mode resume (-c/-s) restores history and the stored model, but not the stored plan/build mode or thinking config — those are TUI/ACP surfaces.

Stats

craft stats reports the usage ledger; --sessions breaks it down per session. In the TUI, /stats and /usage show the same data live.

Headless Mode

Run non-interactively with --print (also spelled -p):

craft --print "summarize the retry logic in agent/src"

Output formats

--output-format selects:

  • text — plain text reply.
  • stream-json — Claude Code-compatible streaming JSON, so scripts written for Claude Code SDK-style agents work unmodified.

--image PATH attaches an image to the prompt.

Prompting

The positional PROMPT is honored by --print and the interactive TUI; piped stdin (echo "do x" | craft, no --print) is read the same way. The positional wins over piped stdin. Empty/whitespace input starts the TUI normally.

In resume sessions (-c / -s) the prompt waits for the session to load, so its first turn runs in the loaded mode.

Permissions

Headless runs enforce the same rules through a permission gate with no interactive approver: unresolved asks fail closed with guidance naming the opt-outs, and denied calls never execute. --yolo (bypass everything) and -A/--auto-review (an LLM reviewer answers asks, fail-closed) are the deliberate opt-outs — mutually exclusive, rejected at startup. The gate covers batch children and subagent dispatch.

Other flags

--max-turns bounds the run; -m/--model provider/model selects the model; --allowed-tools/--disallowed-tools set process-lifetime tool policy (see Permissions). A set of Claude Code SDK compatibility flags is accepted but ignored.

Not yet implemented (flagged with warnings at runtime): --input-format stream-json (SDK mode), verbose transcript output, flow mode.

ACP

craft acp runs an Agent Client Protocol server on stdio, for editor and IDE integration (e.g. Zed and other ACP-speaking clients).

{
  "adapter": { "command": "craft", "args": ["acp"] }
}

What the server exposes

  • Sessions — session/load resumes a stored session through the same transcript builder as /sessions and -s (see Sessions).
  • Permissions — session/request_permission consults the same PermissionManager as every other surface; rule evaluation is identical to the TUI and headless gate (see Permissions).
  • Thinking — a Thinking session option exposes the same controls as /thinking in the TUI (see CLI → Thinking controls).
  • Attachments — client-provided attachments and client MCP servers are supported.

Configuration

Provider and model selection come from the same BML config as every surface (see Configuration); no editor-specific setup exists beyond pointing the client at the binary.

MCP

Connect external tool servers over stdio or HTTP. MCP blocks merge from the global config (~/.config/craft.bml and ~/.config/craft/*.bml) and the project’s .craft/mcp.bml — the project wins on name conflicts.

Stdio transport

command is the program plus arguments:

mcp "filesystem" {
  command = ["npx", "-y", "@modelcontextprotocol/server-filesystem", "/tmp"]
  environment = { API_TOKEN = "${MY_MCP_TOKEN}" }
  enabled = true       # default
  timeout = 30000      # ms, 1..=300000
}

HTTP transport

mcp "remote" {
  url = "https://mcp.example.com/mcp"
  headers = { Authorization = "Bearer ${EXAMPLE_TOKEN}" }
}

headers (with ${VAR} expansion) rides every request to the server.

OAuth

For servers without a registration endpoint, declare a static OAuth client. The callback listener always binds loopback; callback_port fixes the redirect URI’s port so it can be pre-registered:

mcp "acme" {
  url = "https://mcp.acme.example.com/mcp"
  oauth {
    client_id = "acme-client"
    client_secret = "${ACME_CLIENT_SECRET}"
    callback_port = 3118               # fixed loopback port
    callback_path = "/callback"        # default /mcp/oauth/callback
    callback_hostname = "localhost"    # default 127.0.0.1; loopback only
  }
}

Every key except client_id is optional; callback_hostname must resolve to loopback.

Details

  • Names are ASCII alphanumeric + hyphens and must not collide with built-in tools.
  • ${VAR} in environment/headers values expands from the process environment.
  • MCP tools are proxied as portable server__tool names; permission rules can scope them (mcp__server for a whole server — see Permissions).
  • /mcp in the TUI lists connected servers.
  • Craft’s own knowledge layer does not ride MCP — argosy is linked in-process (see Argosy).

Startup prompt

The positional PROMPT is honored by --print and the interactive TUI — craft "do x" submits it as the first message right after provider startup. Piped stdin (echo "do x" | craft, no --print) is read the same way; the positional wins. In resume sessions the prompt waits for the session to load.

Thinking controls

/thinking opens the TUI selector; /thinking low, /thinking adaptive, /thinking off, or /thinking 4096 apply directly. Alt+E cycles. The preference persists with the session, restores on resume, and is inherited by subagents. ACP exposes a Thinking session option.

For headless or startup overrides use one of --thinking <setting>, --effort <level>, or --max-thinking-tokens <positive-count> — mutually exclusive. Seed new sessions in craft.bml:

always_thinking = "low"

Modes are off, adaptive, minimal, low, medium, high, xhigh, max, or a positive token count. An unset preference means off. Providers that cannot disable reasoning use their lowest supported mode; “off” is not a universal promise of zero reasoning.

Per-model models.dev reasoning metadata resolves accepted effort levels. Requests snap to the closest lower supported level, or the minimum accepted level if none is lower. Effort-only and toggle-only APIs cannot enforce a thinking-token budget; numeric settings map to an effort/toggle there. Budget APIs clamp to their published limits and half the effective output window, reserving room for an answer.

Manual model declarations can override supports_thinking, requires_thinking, and reasoning_options; local backends can declare thinking_fields fragments (see Providers).

Development

The CLI harness lives in agent/ (crate craft, binary craft), built on the animist provider/agent/history stack with the argosy knowledge crate linked in-process.

Build and test

cargo test -p craft
cargo fmt -p craft --check
cargo clippy -p craft --all-targets -- -D warnings

ProviderHandle::from_config builds only the selected animist provider; parsing configuration never constructs clients or initiates interactive authentication.

Provider conformance (offline)

src/conformance/ drives every supported kind through a real Conversation against a local mock HTTP server speaking each protocol (Anthropic Messages, OpenAI Responses/Chat Completions, Bedrock Converse with AWS eventstream framing): text, thinking and tool-call round trips, tool-result image placement, retry/reauth/overflow recovery, Bedrock’s in-provider retries, usage, and catalog pricing. It is part of cargo test and needs no credentials.

Live smoke tests (opt-in)

Real model calls, #[ignore]d and env-gated so CI never pays for inference:

CRAFT_LIVE_BASE_URL=http://127.0.0.1:8000/v1 \
CRAFT_LIVE_MODEL=orion-26b \
CRAFT_LIVE_API_KEY=…            # optional for keyless local servers
  cargo test -p craft --lib conformance::live -- --ignored --nocapture

CRAFT_LIVE_KIND selects the config kind (default openai-compatible; llama-cpp, omlx, ollama, anthropic, …). The two tests: a plain text round trip, and a tool round trip that must read a file and quote it back.

Manual QA

The same env serves a manual QA session: run the TUI against a local model (a provider block with the same kind/base_url), exercise tool calls, cancel (Esc), resume (/sessions), and /compact.
